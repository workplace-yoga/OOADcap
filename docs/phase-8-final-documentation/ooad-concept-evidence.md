# Definitive OOAD Concept & Code Evidence Guide

## 1. Object-Oriented Concepts Implemented

| OOAD Concept | Concrete Project Definition | Code Location & Implementation Evidence | Viva Defense & Justification |
| :--- | :--- | :--- | :--- |
| **Encapsulation** | Hiding internal object state and enforcing invariants through public operations. | [`User.js`](../../../backend/src/domain/model/User.js): Private `#passwordHash` field; `authenticate(plain)` hides hash comparison.<br>[`AcademicRecord.js`](../../../backend/src/domain/model/AcademicRecord.js): `validateScores()` bounds marks ($0 \le s \le 	ext{max}$). | Protects domain state from external corruption; guarantees that password hashes and invalid grades cannot be injected. |
| **Abstraction** | Hiding complex persistence and external protocol details behind clean interfaces. | [`SqlUserRepository.js`](../../../backend/src/infrastructure/persistence/SqlUserRepository.js): Repositories hide SQL queries behind `findById()`, `save()`, and `deleteById()`. | Application services work with domain concepts without needing to understand database dialect details. |
| **Inheritance** | Specialization hierarchy sharing identity and credential capabilities. | [`Admin.js`](../../../backend/src/domain/model/Admin.js), [`Faculty.js`](../../../backend/src/domain/model/Faculty.js), [`Student.js`](../../../backend/src/domain/model/Student.js) extend [`User.js`](../../../backend/src/domain/model/User.js). | Eliminates code duplication for authentication, usernames, and email across different institutional actors. |
| **Polymorphism** | Objects responding to the same message interface in role-specific manners. | `User.getDashboardRoute()`: Polymorphically returns `"/admin/dashboard"` for Admin, `"/faculty/dashboard"` for Faculty, and `"/student/dashboard"` for Student. | Eliminates conditional `switch(user.role)` statements in the client router; allows dynamic UI dispatching. |
| **Association** | Structural link representing a peer relationship. | `Course.assignFaculty(facultyId, facultyName)`: Links teaching instructors to course offerings. | Models academic teaching assignments without tight physical coupling. |
| **Composition** | Strong ownership where child lifecycle depends on the parent aggregate root. | `Enrollment` owns `Attendance` and `AcademicRecord` instances via `addAttendance()` and `addAcademicRecord()`. | An attendance or exam record cannot exist without an active course enrollment. |
| **High Cohesion** | Classes focus solely on a single unified domain responsibility. | `Attendance.js` manages session statuses; `AcademicRecord.js` computes grades; `AuthController.js` handles HTTP only. | High maintainability; bugs in mark calculation cannot impact session attendance logic. |
| **Low Coupling** | Minimal direct dependencies between system subsystems. | Frontend interacts with backend solely via HTTP JSON `ApiClient.js`; Services depend on repository contracts. | Enables independent refactoring of UI or database without breaking domain logic. |
| **Single Responsibility (SRP)** | Every class has one reason to change. | `PasswordHasher.js` handles only bcrypt hashing; `TokenService.js` handles only JWT token generation. | Adheres to SOLID design principles. |
| **Dependency Inversion (DIP)** | High-level business policies do not depend on low-level database details. | `StudentService` depends on repository abstractions, not raw database connection pools. | Allows swapping database drivers (SQLite $ightarrow$ Postgres) without changing a single line of business logic. |
